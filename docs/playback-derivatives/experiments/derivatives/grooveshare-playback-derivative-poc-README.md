# Playback Derivative Proof of Concept

## Purpose

This experiment evaluates whether GrooveShare can use smaller server-generated playback derivatives to reduce project-open latency without compromising the authoritative Web Audio timeline, synchronization, alignment, or recording placement.

The original media remains the authoritative source asset. A derivative is a replaceable playback representation.

## Baseline Problem

A representative GrooveShare Labs track measured approximately:

- Duration: ~148 seconds
- Original size: ~37–39 MB
- Network transfer time: ~2.4 minutes
- Browser `decodeAudioData()` time after download: ~0.1–0.2 seconds

The dominant readiness bottleneck is therefore network transfer size, not Web Audio decoding.

## Tooling

- FFmpeg 9.0.1 with `libopus`
- FFprobe
- Chrome Web Audio API / `decodeAudioData()`

Candidate derivative settings tested:

- Ogg Opus
- 48 kHz stereo
- VBR
- `application=audio`
- 192 kbps target
- 256 kbps target

Example commands:

```powershell
ffmpeg -y -i music-test.wav -c:a libopus -b:a 192k -vbr on -application audio -ar 48000 -ac 2 music-test-192.opus
ffmpeg -y -i music-test.wav -c:a libopus -b:a 256k -vbr on -application audio -ar 48000 -ac 2 music-test-256.opus
```

## Timing Fixture

A 150-second, 48 kHz, stereo, 24-bit PCM WAV fixture was created with short timing markers at 1, 11, 21, 31, 41, 51, 61, 71, 81, 91, 101, 111, 121, 131, and 141 seconds.

Fixture properties:

```text
codec_name=pcm_s24le
sample_rate=48000
channels=2
duration=150.000000
size=43200102
```

The fixture was designed to detect both fixed codec offset and accumulated drift.

## Browser Timing Results

Chrome decoded the WAV and both Opus derivatives through Web Audio. All three decoded to exactly:

```text
duration: 150.000000 sec
samples:  7,200,000
sample rate: 48,000 Hz
```

FFprobe reported the Opus container duration as `150.006500` seconds, but Chrome's Web Audio decoder produced the same decoded timeline length as the WAV.

### 192 kbps target

```text
Mean offset:       +0.0115 ms
Minimum offset:    +0.0102 ms
Maximum offset:    +0.0149 ms
First→last change: ~0.0000 ms
```

### 256 kbps target

```text
Mean offset:       +0.0111 ms
Minimum offset:    +0.0101 ms
Maximum offset:    +0.0139 ms
First→last change: 0.0000 ms
```

At 48 kHz, one sample is approximately `0.0208 ms`. The measured displacement was therefore below one sample, with effectively zero accumulated drift over 150 seconds.

### Timing Conclusion

Ogg Opus generated by FFmpeg/libopus and decoded by Chrome Web Audio appears temporally equivalent to the WAV source for GrooveShare's purposes.

The experiment found no evidence that GrooveShare needs user-facing derivative alignment, separate derivative transport math, a second playback clock, drift correction, or a separate derivative placement system.

## Real Music Size Test

Representative music source:

```text
filename=music-test.wav
duration=147.692313
size=39079430
bit_rate=2116802
```

192 kbps target:

```text
filename=music-test-192.opus
duration=147.698833
size=4109008
bit_rate=222561
```

Approximate result: 4.1 MB, ~89.5% smaller, ~9.5x size reduction.

256 kbps target:

```text
filename=music-test-256.opus
duration=147.698833
size=5243534
bit_rate=284012
```

Approximate result: 5.24 MB, ~86.6% smaller, ~7.5x size reduction.

The average bitrates exceed the nominal targets because VBR was enabled.

## Listening Test

A randomized A/B/C comparison used the original WAV, 192 kbps Opus, and 256 kbps Opus. The versions were very difficult to distinguish reliably. The listener slightly preferred the 256 kbps derivative.

There was no clear subjective indication that either Opus derivative was unsuitable for normal GrooveShare playback or as backing audio while recording.

## Milestone 1 Decision

**GO**

Initial playback derivative specification:

```text
Container:     Ogg
Codec:         Opus / libopus
Sample rate:   48 kHz
Channels:      stereo for the current stereo source case
Bitrate:       256 kbps target
Rate control:  VBR
Application:   audio
```

### Why 256 kbps

192 kbps was also viable and smaller, but 256 kbps is the conservative initial choice because it was slightly preferred in the listening test, musicians may record while monitoring derivatives, and it still reduced the representative track from ~39.1 MB to ~5.24 MB.

The bitrate should be treated as a configurable/versioned derivative-generation setting so GrooveShare can regenerate derivatives later without changing the media model.

## Architectural Invariants Going Forward

1. The original remains the authoritative media asset.
2. Derivatives are disposable and regeneratable.
3. Derivatives must remain temporally equivalent to originals.
4. Users never align derivatives separately.
5. The existing authoritative Web Audio transport and scheduler remain in control.
6. Playback and recording may use derivatives once required derivatives are ready.
7. Original availability should not gate recording merely because originals are still downloading.
8. Server-side tooling owns transcoding and derivative generation.
9. Any codec/container delay compensation, if ever required, is an internal media-pipeline concern and never user-facing.
10. Timing equivalence must be protected by automated tests.
